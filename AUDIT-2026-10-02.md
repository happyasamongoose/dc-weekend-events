# Second audit — DC Weekend Events Planner

> **Status:** R1–R9 addressed on `claude/weekend-planner-build-audit-4mtzae`; see the
> commit that follows this note for what changed, and the manual-dispatch results
> recorded at the bottom.

Audited 2026-10-02 against `main` @ `b499087`, five weeks after the first audit's
fixes merged (PR #1, 2026-08-29). Evidence: the Actions run history, the failing
job's log, issue #2, the Pages deploy log, and the file the site is serving.

## Verdict

**The weekly refresh has failed every Thursday since the fixes went live — five
for five — and the cause is my change.** The site has been serving the 2026-08-27
listings for 35 days. The safety net I built behaved exactly as designed: the old
file stayed published, the page has shown its stale banner since about Sep 6, and
an issue was filed on the first failure and updated on each one since. Nobody saw
any of it, which is the second finding.

What I got wrong, specifically: the first audit's own rule — *verify against one
live dispatch before relying on it* — was applied to structured outputs and not to
the model-and-search-tool swap or to search-domain filtering. Two untested live-API
changes shipped. One of them broke the pipeline; the other may be hurting results
and there is one data point suggesting so.

The fix is small and is spelled out under R1. Next scheduled run: Thursday Oct 8.

---

## R1 · Critical — every request times out

`REQUEST_TIMEOUT_MS` is 120 seconds. It predates my change and fit the old setup;
it does not fit the new one. In the Oct 1 run, six of seven tracks hit the cap on
both attempts. The one request that completed took **119 seconds** on its retry.

| run | code | sweep step | result |
|---|---|---|---|
| Aug 20 | old | 1m 56s | success |
| Aug 27 | old | 3m 41s | success |
| Sep 3 | new | 6m 32s | 6 tracks timed out → safety abort |
| Oct 1 | new | 12m 39s | 6 tracks timed out → safety abort |

The old sweep finished all seven tracks, three at a time, in under four minutes —
roughly 40–75 s per request. After the swap to `claude-sonnet-5` plus
`web_search_20260209` (whose dynamic filtering runs code execution under the hood)
plus a 16 000-token output ceiling, a request takes two minutes or more. Every one
of them is cut off; the retry is cut off too; the run aborts at zero events.

Fix, in order of certainty:

1. Raise the per-request cap to 8 minutes and the job's `timeout-minutes` to 30
   (seven tracks, three concurrent, worst case ~24 min).
2. Stop retrying a *timeout* with the same timeout — it only doubles the wasted
   wall-clock. Retry 429/5xx as before.
3. Then measure one manual run before Thursday (see R5). If requests still
   run long, the cheaper lever is the tool: `web_search_20250305` is the basic,
   faster variant and was what the working pipeline used.

## R2 · High — the one track that finished returned nothing

Track 6 (music) completed with 6 searches, 125 591 input tokens and 3 859 output
tokens — and `parseEventArray` found **zero events** in it. The log shows nothing
about why, because nothing logs the model's text when a track yields nothing.

Two candidates. Track 6 is one of the three I restricted with `allowed_domains`,
so the model may have been confined to twelve venue domains that the new tool's
filtering found nothing date-specific on, and honestly answered with an empty list.
Or the text came back in a shape the scanner doesn't expect. Either way this is
the search-domain decision's first live data point, and it is bad.

Fix: log the first 300 characters of model text whenever a track returns zero
events; run track 6 once with `searchDomains` and once without; and turn the
restriction **off** for tracks 5–7 until a run shows it finding events. The
link-side allowlist still protects what gets published.

## R3 · High — the alarm rang for 29 days and nobody heard it

Issue #2, "Weekly events refresh failed", was opened by the Sep 3 run and has a
comment from each run since. It has no assignee and no label, so it generated no
notification to a person — it sat in a repo nobody opens. The stale banner has
been live on the page since about Sep 6 and did its job, but a banner on a page
the family stopped opening is not an alert either.

Fix: create the issue with `--assignee happyasamongoose` (an assignment emails
the owner), and put the last 15 lines of the sweep log in the issue body so it
says *why* — "6 tracks timed out" is actionable; "it failed" is not. Watching
the repository in GitHub's notification settings is the belt to those braces.

## R4 · Medium — the cost of a failed run is invisible

The abort line reports **$0.35**, which is the one request that completed. The
twelve requests that were aborted client-side are not counted, and the API very
likely finished and billed them. Five weeks of that is unknown spend — check the
console's September usage. Fix: count attempted requests on the abort path, not
only completed usage.

## R5 · Medium — no way to validate a change short of waiting for Thursday

This is the process gap behind R1 and R2. Add two `workflow_dispatch` inputs:
`tracks` (run only the listed track numbers) and `dry_run` (skip the commit).
Running track 6 alone costs cents and takes minutes, and would have caught both
regressions before the merge.

## R6 · Low — the pinned actions target deprecated Node 20

Every run now warns that `actions/checkout@v4` and `actions/setup-node@v4` target
Node 20 and are being forced onto Node 24. Harmless until GitHub removes the shim.
Bump to `checkout` v6.1.0 (`d23441a48e516b6c34aea4fa41551a30e30af803`) and
`setup-node` v6.5.0 (`249970729cb0ef3589644e2896645e5dc5ba9c38`).

## R7 · Low — "Thursday morning" is soft

The cron is 10:00 UTC; the five runs fired between 13:55 and 16:46 UTC. GitHub
delays busy cron slots. Either move it to a quieter minute (`17 5 * * 4`) or
soften the wording in SETUP.md and the user guide.

## R8 · Low — the page past the end of its data

Today "This Weekend" resolves to Oct 3 from the Aug 27 file — 12 one-off events,
10 runs, 10 always-on. From Oct 5 every covered weekend is in the past and the
picker clamps to Oct 3, still labelled "This Weekend", with the stale banner above
it. An explicit state — "No current listings; last refreshed Aug 27" — would be
more honest than stale cards under a current-sounding label.

## R9 · Info — the allowlist has no maintenance loop yet

No run has got far enough to show it, but when a new legitimate venue host appears
its events are dropped and the only trace is a line in the Actions log. Surface the
drop tally in the failure issue (R3) or a run summary so additions are visible.
